# ODAS v0.3 — Security review and experimental release gate

Date: 2026-11-01
Status: preliminary maintainer review; **not an independent audit**.
Scope: `src/odas/dkim_verify.py`, `src/odas/dkim_multi.py`, test suite, and GitHub Actions.

## Threat model
Untrusted inputs include raw RFC5322 message bytes, DKIM-Signature headers, DNS names, DNS TXT records and errors returned through the caller-provided lookup callback. The adapter must not turn a parsing error, DNS outage, or missing optional dependency into a claim of malicious activity. A passing DKIM signature authenticates a signing domain's responsibility for selected message bytes; it does not establish the sender's real-world identity, message safety, or DMARC alignment.

## Current protections
- Maximum message size of 256,000 bytes; bounded multi-signature count.
- Cryptographic verification delegated to optional dkimpy; genuine RSA integration fixtures exist.
- DNS callback failures are generally reported as indeterminate.
- Multi-signature observations keep per-signature status and only report signing domain for a passing signature.
- Outputs explicitly state `no-blocking-decision`; no SMTP enforcement.

## Outstanding security work (required before production use)
1. **Resolver contract:** define strict name validation, TXT-answer size and count, timeout/deadline, retries, caching, DNSSEC and transport assumptions. A Python callback cannot be forcibly timed out merely by passing a numeric timeout to the verifier. Never assume a user-supplied resolver is safe.
2. **Header ambiguity:** test duplicate From and DKIM-Signature fields, folded header values, CRLF violations, Unicode/IDNA edge cases and malformed signatures. Do not extract identity from raw header text if it conflicts with the cryptographic library's parsed signature.
3. **Multiple signatures:** explicitly distinguish per-signature pass/fail/indeterminate from overall message authentication. Document behavior when a pass coexists with an indeterminate signature. No alignment inference.
4. **Resource limits:** bound header bytes, total DNS lookups, per-lookup response size and cumulative DNS work. Avoid unbounded callbacks and log amplification.
5. **Error semantics:** classify permanent malformed signatures separately from temporary DNS failures without disclosing sensitive message material.
6. **Privacy:** no raw message/header/body logging by default. Define retention, redaction, data access and deletion before field pilots.
7. **Authentication roadmap:** SPF requires authenticated connecting IP and envelope sender; DMARC requires RFC5322.From alignment with validated SPF or DKIM; evaluate forwarding, mailing lists and ARC separately.
8. **Dependency review:** pin and scan dkimpy and cryptography dependencies, document supported Python versions and run independent code review.
