# ODAS v0.2: Authentication Evidence (experimental)

This stage adds an observation-only interface for *externally verified* SPF,
DKIM, DMARC and ARC result labels. It does not perform DNS queries,
cryptographic verification, SMTP interception, or blocking.

## Trust boundary
An email's Authentication-Results header is attacker-controlled unless a
receiving gateway has established its provenance. Do not pass header claims
directly into trusted evidence. An eventual integration must authenticate
the gateway, strip or distinguish untrusted upstream headers, bind its
verification result to the exact message and protect the result in transit.

The `trusted_gateway` flag is a developer-controlled trust-boundary marker,
not an authentication mechanism. It MUST NOT be set based on user-provided
email data, request parameters or arbitrary JSON.

## False positives
SPF failures can be caused by forwarding; mailing lists can alter DKIM;
DMARC outcomes require alignment and policy context. ARC is not a blanket
exemption. No individual result establishes abuse or safety.

## Road to actual verification
1. Design a message-bound authenticated gateway adapter.
2. Integrate maintained SPF/DKIM/DMARC verification libraries and DNS checks.
3. Test forwarding, mailing lists, malformed inputs, DNS failures and spoofing.
4. Measure false positives in opt-in shadow-mode pilots.
5. Only later consider reversible quarantine under operator control.
